## 三、仍需治理的二轮后续项

| 优先级 | 事项 | 当前问题 | 验收标准 |
|---|---|---|---|
| P0 | 跨模块 facade 收敛 | 部分 `application` 仍直接依赖其他模块 `infrastructure` | 跨模块访问只通过 `application facade` 或共享契约，不直接注入对方 Mapper / Entity |
| P0 | Auth 与 User 边界收敛 | 登录、会话、当前用户仍共享 `UserAccount` 与用户仓储细节 | `auth` 只依赖用户查询 facade，不依赖 `user.infrastructure` |
| P0 | Tenant 与 Resource / Role / Dept / User 边界收敛 | 租户初始化、套餐能力、默认角色部门存在跨模块基础设施访问 | 租户生命周期通过目录、角色、部门、用户 facade 完成初始化 |
| P1 | Resource 与 Role / Tenant 边界收敛 | 资源授权和租户覆盖仍直接访问角色、租户表 | 资源模块只维护资源树和权限码，授权关系通过角色/租户 facade 协作 |
| P1 | System 与 Audit 边界收敛 | 分类规则统计仍直接读取审计表 | 审计模块提供只读统计 facade，系统模块不依赖审计 Mapper |
| P1 | `config` 过渡区拆分 | 业务配置与技术配置仍部分混放 | 技术配置归 `infrastructure/config`，业务策略配置归属模块 |
| P1 | `security` 过渡区拆分 | 当前用户、安全缓存、Sa-Token 胶水仍在同一过渡区 | 当前用户语义归 `auth`，Sa-Token 技术适配归 `infrastructure/security` |
| P2 | 测试包路径同步 | 部分测试包名仍保留历史语义 | 测试包路径与目标模块路径一致，便于按模块定位 |

## 五、下一阶段执行顺序

1. 先收敛 Auth → User 的查询 facade，避免认证模块直接碰用户基础设施。
2. 再收敛 Tenant 初始化链路，拆出 User / Role / Dept / Resource 的最小应用 facade。
3. 然后处理 Resource 授权链路和 System → Audit 统计链路。
4. 最后拆 `config` 与 `security` 过渡区，并同步测试包路径。

执行原则：每次只处理一组跨模块依赖，保持后端测试全绿后再进入下一组。
